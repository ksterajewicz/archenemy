# AGENTS.md

Instructions for AI agents (Claude Code, Copilot, Cursor, and others — whatever
tool each contributor uses) working on this repository. Goal: every agent,
regardless of operator and tool, should keep the project consistent and break
nothing. This file is the single source of such instructions in the repo —
there's no `CLAUDE.md` or other per-tool file here; if your agent reads a
different format, start from this file and point it here.

## Before you start — session start

1. Read `README.md` (repo structure, the four layers, installation).
2. Check `packages/requirements-*.txt` and `packages/additional-packages-*.txt`
   — what's actually supposed to be installed.
3. If the task touches an unfamiliar module — open it and read it before
   writing a line of code.
4. Don't assume something works the way its name suggests — verify against
   the source (the repo's code, or Hyprland/waybar documentation), not from
   memory.

## Stack

- Bash (scripts) + Hyprland configuration in **Lua** (as of Hyprland 0.55 the
  old hyprlang `.conf` format is deprecated, and 0.57 removed it; old files
  stay alongside as `*.conf.bak` until the migration is fully verified on a
  live machine — `hyprlock.conf` and `hyprpaper.conf` deliberately STAY in
  hyprlang, they're separate programs, not Hyprland).
- **`hyprctl dispatch` takes a Lua expression** (`hyprctl dispatch X` runs
  `hl.dispatch(X)`): `hyprctl dispatch 'hl.dsp.focus({ workspace = "2" })'`.
  The old form (`hyprctl dispatch workspace 2`) is a Lua syntax error and
  scripts usually hide the output, so the action silently doesn't happen;
  `tests/repo-hygiene.sh` guards this. Parsers of `hyprctl` text output must
  accept both `workspace N` (0.57+) and `workspace ID N` (older).
- One component in C: `src/flux-wall/` — the animated wallpaper (Wayland
  `wlr-layer-shell` + EGL + GLES 3.0). Optional: built by `install.sh` step
  [9.6] with a fallback; a missing compiler/dependency doesn't block the
  rest of the install.
- No repo-level build system (aside from `make -C src/flux-wall`) and no
  custom package manager — everything goes through `pacman`/AUR (`yay`),
  with lists in `packages/`.

## Architecture — four layers (NEVER mix them)

| Layer | Where it lives | In git? |
|---|---|---|
| **Rice** (looks) | `rices/<name>/`, symlinked into `~/.config` | yes |
| **Shared** (binds, media keys, general Wayland env) | `config/hypr/*.lua` | yes |
| **Machine** (monitors, GPU env, hardware keys, workspaces) | generated by `install.sh` into `config/hypr/` | NO (gitignore) |
| **Personal** (user autostart, user app binds, mouse settings) | `config/hypr/autostartpersonalisation.lua`, `config/hypr/appbinds.lua`, `config/hypr/mouse.lua` (from `data/mouse-sensitivity.dat` and `data/mouse-settings.dat`, only via `scripts/hypr/mouse-settings.sh` / `Super+A → [m]`; parity rices `require_optional` it after their `input` block, beta does not), `config/hypr/keyboard-layouts.lua` (from `data/keyboard-layouts.dat`, 1–4 XKB layouts in order, only via `scripts/hypr/keyboard-layouts.sh` — `Super+A → [k]` and the parity-rice binds `Super+Ctrl+1…4` = `switch N`; `Super+K` stays `switchxkblayout all next`), `config/shell/shellrc` (the user's aliases, functions and PATH for bash and zsh) and `config/shell/keys.zsh` (the user's zsh vi-mode key, only via `scripts/shell/lib/shell-rc.sh` and `[h] → 4`) and `config/shell/plugins.zsh` (optional zsh plugins, only via the same library and `[h] → 5`), and `config/shell/cli-tools.bash` / `cli-tools.zsh` (optional CLI choices per shell, same library and `[h] → 6`) | NO (gitignore) |

The optional music stack (`config/mpd/`) follows the same split: `mpd.conf` is
shared (tracked), `output.conf` (audio output, rewritten by `Super+A → [o] → 3`) is
machine, `local.conf` is personal — both generated by `install.sh` [8l] and
gitignored. `config/applications/ncmpcpp.desktop` is a tracked template that
[8l] *copies* (never links) into `~/.local/share/applications`.

Rules that follow directly from the table:

- No monitor names, GPU vendors, hostnames, or personal apps in tracked
  files. If something like that shows up in your diff — that's a sign it
  should be generated, not committed.
- `install.sh` must create EVERY generated file (even empty ones) — the
  rices' `hyprland.lua` `require()`s/`source`s them, so a missing one breaks
  startup.
- New machine/personal content → add the pattern to `.gitignore`.

## Known pitfalls (don't rediscover them twice)

- **waybar `custom/*` module `interval` MUST be an integer (seconds)
  ONLY.** Waybar 0.15.0 casts the fraction to `long` BEFORE multiplying by
  1000 — `0.5` becomes **1 ms**, i.e. a fork loop of the script running
  non-stop, separately on each monitor. Always force an immediate module
  refresh via a signal (`pkill -RTMIN+N waybar`) from the state-changing
  action, never by shortening the interval.
- **A running waybar never re-reads `config.jsonc`.** Waybar 0.15.0 loads
  the config only at start (`src/client.cpp`, `Client::main`); inotify
  (`"reload_style_on_change"`) watches `style.css` only. A `git pull` or
  `[u]` under a running bar applies the new CSS at once but keeps the old
  modules: a new module or `"signal"` does not exist yet, `pkill -RTMIN+N`
  still exits 0 (the process got it) and nothing changes until waybar
  restarts — on the owner's laptop that looked like "the bar logo needs a
  reboot" (2026-11-19). `scripts/waybar/lib/waybar-reload.sh`:
  `waybar_config_stale` (config mtime through the rice symlink not older than
  the start of a `waybar` process, `ps -o etimes=`) and `waybar_reload`
  (`pkill -USR2 -x waybar` = the default `on-sigusr2: reload`, config + CSS +
  module scripts). `bar_change_report` uses them, and `update-archenemy.sh`
  reloads after a pull that changed the config or `scripts/waybar/`;
  Super+T restarts waybar anyway.
- **Rice switching is 2-line stubs** in
  `scripts/changing-theme-scripts/*.sh` (the file name = the rofi menu
  label; the `RICE_NAME` inside must match the `rices/<folder>` folder
  name). ALL the logic lives in `scripts/changing-theme-scripts/lib/switch-rice.sh`
  — edit the library, never paste logic back into a stub (that's how
  copy-paste parity drift happens).
- **A new rice is listed by name in several places** besides its folder and
  stub (checked when `yin` was added, 2026-11-17): `install/install.sh` [8h]
  (`hyprlock-background-<rice>.conf`), `.gitignore`, `HYPRLOCK_BG_FILES` in
  `scripts/rofi/rofi_wallpaper_switcher.sh`, `known_rices` in
  `scripts/archenemy-doctor.sh`, `MOTIFS` in
  `scripts/wallpapers/gen_rice_preview.py` (its `preview.png`), and the
  hard-coded rice lists in `tests/` (`install-main`, `bluetooth`,
  `keyboard-layouts`, `mouse-settings`, `rofi-clipboard`, `font-settings`,
  `flux-wall-dither`). Suites that glob `rices/*/` (`rice-autostart`,
  `tui-contrast`, `rofi-inputbar`, `rofi-theme-switcher`) pick it up alone.
- **Monitors are identified by `desc:<EDID description>`, never by connector
  name.** `eDP-2`/`HDMI-A-1` became `eDP-1`/`HDMI-A-3` after a reboot on the
  owner's laptop (2026-09-21) and every rule of the machine layer stopped
  matching. `scripts/hypr/lib/monitor-id.sh` (`monitor_selector_from_dat`,
  `monitor_live_name`, `lua_string`, `lua_comment`) is the only place that
  turns a `data/monitors/*.dat` into a selector or a live connector name — use
  it in anything that writes a monitor into a generated file or talks to
  `hyprctl`/`hyprpaper` about a specific output; a raw `MONITOR=` value is
  only good for "is this the built-in panel" and for file names. Names go into
  generated Lua only through `lua_string` (values; control characters become
  `\ddd`) or `lua_comment` (comments; control characters become `?`): a raw
  CR or newline ends a Lua string or comment and breaks the whole file.
- **Integrity rule for the machine layer (public project — other
  people's machines).** A generated file describes the machine *on the day
  of installation*, and Hyprland never complains when reality drifts — it
  silently falls back. So: (1) every identifier written into a generated
  file must be stable across reboots (`desc:` from EDID, not a connector
  name), (2) every new mechanism must degrade to the previous behaviour on
  the edge cases — missing EDID, duplicate descriptions, special
  characters, `.dat` files from an older version — never below it, and (3)
  a drift must become **one visible notification with the fix**, not a
  silent fallback: extend `scripts/hypr/machine-layer-check.sh` when you
  add a generated file or a new kind of selector.
- **One monitor = one key, and the runtime call uses the same key as the
  generated file.** hyprpaper stores its settings as a list, gives a monitor
  the **first matching** entry (`WallpaperMatcher.cpp::matchSetting`: connector
  name literally, `desc:` by prefix) and lets IPC append an entry at the end,
  replacing only one with an identical key (`addState`). So a second entry for
  the same screen (its old connector name left in `data/wallpaper.dat`) or an
  IPC call keyed differently than the config **silently wins the match** and
  the change never reaches the screen, while `hyprctl` reports success
  (2026-09-22: "I pick another wallpaper, nothing changes"). Migrate old keys
  on read, and confirm the result (`hyprctl hyprpaper listactive`) instead of
  trusting an exit code — success is an observed state change.
- **flux-wall: never read the accumulator at exactly one computed column.**
  A particle stamp (`GL_POINTS`, size 1) aimed at pixel centre `xc` lands at
  `xc-1` on the right half of the screen (float error at NDC > 0 — measured
  offscreen 2026-09-21: left half 937 stamps in `xc`, right half all in
  `xc-1`). Read a band (`xc-1..xc+1`) and keep other stamps out of
  `xc±2`; `bash tests/flux-wall-bars.sh` (after `make -C src/flux-wall
  tools`) renders both monitor sizes and checks both halves.
- **flux-wall: the Bayer raster only when the `dither` uniform is 1 —
  dither is a property of the rice, not of the animation.** Owner's report
  2026-09-25: music visualizations came out rastered in rices that have
  nothing to do with dither. The raster is declared per rice
  (`FLUX_WALL_DITHER=1` only in `rices/dither-flux/flux-wall.conf`; missing
  key = 0), `flux-wall.sh` turns it into `--dither`/`--no-dither` for
  whatever animation is picked, and the binary defaults to smooth. Every
  shader that quantizes must branch on `dither > 0.5`: the rastered branch
  stays pixel-identical, the smooth one maps the same tone onto the palette
  gradient (`palette_ramp`) — never hard-code `bayer8` unconditionally in a
  new shader, and don't encode the look in the name (`dither-*` names stay
  only because renaming would break saved `Super+W` choices).
  `bash tests/flux-wall-dither.sh` checks both the wrapper and every shader.
- **flux-wall: "running" means the first frame reached the screen.** A
  live process proves nothing: the shader compiles and the EGL surface is
  created only at the first configure, so exit code 3 arrives after the
  wrapper's old 0.5 s check (audit 2026-11-05, F7). `flux-wall.sh start`
  passes `--ready-file` and waits for the PID file the binary writes after
  its first successful swap (`FLUX_WALL_READY_TIMEOUT`, default 10 s);
  keep that call after `eglSwapBuffers` in `render_output`. The ready file,
  like the log, lives in `archenemy_runtime_dir` (session files below);
  without such a directory `start` cannot confirm the frame and exits with 3
  (process left running), never "running" and never a wait on a missing file.
  `bash tests/flux-wall-wrapper.sh` checks start/stop/off/status/doctor
  effects on a fake binary whose PIDs are the only ones pgrep/pkill see.
- **flux-wall: exit code 3 only before the first frame.** Until the first
  frame is on screen (the moment `--ready-file` marks), an EGL error ends
  the process with 3 (the wrapper reports it, hyprpaper stays). After that, an
  EGL error on one monitor's surface (e.g. a newly connected monitor)
  tears down only that surface, and the main loop recreates it after 1 s,
  doubling up to 30 s; other monitors keep animating (audit 2026-11-05,
  F4). `EGL_CONTEXT_LOST` is the exception to "skip the frame and try
  again": it never passes, so skipping froze the picture forever while
  the process (and `flux-wall.sh status`) looked alive (F5). It creates a
  new context, engine and all surfaces; more than 3 losses in 60 s = exit
  3. Check `eglGetError()` right after every failed `eglMakeCurrent` /
  `eglSwapBuffers` and pass it through `flux_egl_action`. The decisions
  live in `src/flux-wall/recovery.h` (no Wayland/EGL calls, tested by
  `make -C src/flux-wall test`); `main.c` only carries them out — don't
  add a new `die(3, …)` on a path reachable after start.
- **flux-wall: every shader declares `precision highp sampler2D;`** — each
  `.frag` and every GLSL source built into `engine.c` that uses a sampler
  (vertex shaders included), before the first `sampler2D`. GLSL ES 3.00
  defaults samplers to `lowp`; Mesa honours it and rounds `texelFetch`
  results (particle positions came back with ~8-bit precision), NVIDIA
  ignores it, so the bug is invisible on NVIDIA. `*.update.glsl` files get
  it from `UPDATE_PRELUDE`. `bash tests/flux-wall-shaders.sh` checks it.
- **Machine generators are a single source of truth**:
  `scripts/hypr/lib/gen-workspaces.sh` and `gen-autostart.sh` are called
  from both `install.sh` and the live switchers (`workspace-mode-switch.sh`).
  The same goes for `install/bootloader.sh` (sourced by the CPU/kernel
  installers). Don't duplicate this logic across scripts.
- **Switching rice removes ALL symlinks in `~/.config` pointing into
  `rices/` before linking the new rice.** Without this, the previous rice's
  theme leaks through folders the new rice doesn't overwrite. Preserve this
  invariant whenever you change the switcher.
- **Never delete the user's own config in `~/.config`.** A real directory OR
  a symlink pointing outside `rices/` (e.g. GNU stow) where a rice folder
  goes is moved to `<name>.bak-<timestamp>`, never `rm`'d; links are made
  with `ln -sfn`. The switcher runs under `flock` (a second `Super+T` waits
  and wins; still busy after `SWITCH_RICE_LOCK_WAIT` seconds, default 30 →
  notification, code 1, nothing changed); every background process it starts
  gets `9>&-`, or it would hold the lock for the whole session.
  `bash tests/switch-rice.sh`.
- **Never touch what home-manager manages (D10).** A link into `/nix/store`
  (directly, via `~/.config`, a link chain or a file inside a real rice
  folder) is HM's: `scripts/lib/hm-conflict.sh` (`hm_rice_conflicts`) runs
  in `lib/switch-rice.sh` after the lock and BEFORE the cleanup loop —
  conflict = advice on stderr, notification (not in link-only), exit 3, no
  `.bak`, no `ln`, no `.current_rice`. `install.sh` [9] checks first and
  does not call the library; [8l] does not offer to replace an HM mpd
  config; `rc_block_ensure` returns `managed` (no backup, no write through
  the link), `rc_migrate_apply` refuses and `archenemy_alias_move` returns 2
  before any write (no alias in `shellrc`, no backup; [8m] and `[h]` say the
  old alias stays in HM). Never advise HM `force`. Test
  hook `ARCHENEMY_NIX_STORE` only with `ARCHENEMY_TEST=1`
  (`bash tests/hm-conflict.sh`).
- **Session files (locks, Super+Tab state, logs) live only in
  `archenemy_runtime_dir` from `scripts/lib/runtime-dir.sh`**, never in
  `${XDG_RUNTIME_DIR:-/tmp}`: in a shared `/tmp` another user can create the
  file first, take the lock, read the log or plant a command for Super+Tab. The
  function returns `$XDG_RUNTIME_DIR`, `/run/user/<UID>` or a `0700`
  `archenemy-<UID>` directory in `$TMPDIR`/`/tmp`, each only if it is ours, a
  real directory and private; otherwise it fails and the caller refuses
  (rice switch, window history, guard) or skips the lock or log.
  `bash tests/runtime-dir.sh`.
- **Monitors: `scripts/hypr/monitor-settings.sh` (`Super+A → [n]`) is the only
  live way to change them**, including a new monitor, renumbering and forgetting an
  unplugged one. `lib/gen-monitors.sh` and `lib/gen-workspaces.sh` are the only
  generators, shared with `install.sh`. A change is a trial: without `y` in 15 s, on
  a config error or on SIGHUP all of `data/monitors/` and both Lua files go back,
  because a wrong mode can give a black screen. A `.dat` file name is not a connector
  name: it can carry a suffix (`HDMI-A-1-2.dat`) when an unplugged monitor holds that
  name, so read `MONITOR=`. Use the file name as the key in generators, because it is
  unique. `tests/monitor-settings.sh`.
- **Shell: `scripts/shell/lib/shell-rc.sh` is the only code that writes
  `config/shell/shellrc`, `config/shell/keys.zsh`, `~/.bashrc` or `~/.zshrc`**
  (sourced by `install.sh` [8m] and `scripts/shell/shell-settings.sh`, `Super+A → [h]`). The rc files get only the
  marked block `# >>> archenemy shell >>>` … `# <<< archenemy shell <<<`; every
  change keeps `<rc>.bak-<timestamp>` and writes through the file (a stow symlink
  stays a symlink); a block without its end line is never touched. `install.sh`
  stays silent: shared file + `~/.bashrc` block only, no shell choice, no moving of
  user lines — choosing the shell (`chsh`, zsh package) and moving lines happen in
  the TUI after a `[Y/n]`; success of `chsh` = the passwd entry read back. The
  `archenemy` alias lives in the shared file (marker
  `# archenemy: TUI (Super+A) as a command`); an old one in `~/.bashrc` is moved,
  and the older Polish marker `# archenemy: TUI (Super+A) jako komenda` is still
  recognised and rewritten in place (with a backup). Everything archenemy writes
  to the user's shell files, the shared `config/shell/` layer and the step [8m]
  messages are English (code comments elsewhere stay Polish); `tests/shell-rc.sh`
  checks a fresh `HOME` for Polish text.
  `config/shell/zsh-defaults.zsh` is the tracked shared layer for zsh (no
  frameworks); personal `keys.zsh` loads after it and before `shellrc`, so
  the user's own `bindkey` lines win. Leave zsh's default `^X^V` binding in
  place. Static emacs-mode bindings are sourced from the ZLE Standard Widgets
  documentation in `emacs-default-bindings.txt`. `tests/shell-rc.sh`,
  `tests/shell-settings.sh`.
  Personal `plugins.zsh` defaults to all plugins disabled; zsh-completions
  remain available while their package is installed (the toggle only registers
  a missing system path); `[h] → 5` uses the
  shared `tui_menu` checklist (Space/Enter toggles). Only `shell-rc.sh` writes
  it, with a marker, SHA-256 checksum and dated backups; custom content is refused. Package
  installs always need `[y/N]`, including after the `[Y/n]` autosuggestions
  offer following a successful switch to zsh. Register completion paths before
  `compinit`, load plugins at the end of the managed rc block after `shellrc` and CLI
  initialization, and source syntax highlighting last within that block. User
  code after the block still runs later. Skip missing files and preserve user plugin variables.
  Platform (D8): `shell-settings.sh` takes `pkg_route` from `install/lib/pkg.sh`
  (never an inherited variable); Arch and derivatives run the pre-D8 code
  unchanged (pacman/chsh; `SHELL_PLATFORMS_REV=<rev> bash
  tests/shell-platforms.sh` compares output, commands and HOME files).
  Fedora/NixOS go through `pkg_installable`/`pkg_installed`/`pkg_install`/
  `pkg_hint` with the same consents and defaults; state is written only after
  the package AND the plugin file (`shell_plugin_found`) or the command is
  confirmed. NixOS: no `chsh`, `sudo` or installation, not even in advice
  text — `users.users.<name>.shell`, `programs.zsh.enable`, `pkgs.*`.
  `shell_plugins_v1_text` is frozen (Arch output); new platforms use
  `shell_plugins_v2_text` with paths from `shell_plugin_paths` only.
  Runtime tests set os-release explicitly and copy `install/lib` + the map.
  `tests/shell-plugins.sh` uses mocks without requiring zsh or pacman.
- **Optional CLI tools:** `[h] → 6` uses `tui_menu` for shell selection and each checklist. The trusted catalog `config/shell/cli-tools.tsv` supplies packages, commands, licenses, support and initialization; one row extends the menu without code changes. All tools default off independently for bash/zsh. Only `shell-rc.sh` writes personal `cli-tools.bash` / `cli-tools.zsh`, with marked blocks, dated backups, idempotence and custom-content/symlink refusal. The rc block loads the selected file after `shellrc`. Missing commands require `[Y/n]` before `sudo pacman -S --needed`; verify the command exists afterwards. Disabling removes only the initialization block and keeps packages. Plain PATH tools cannot be hidden per shell. zoxide must preserve `cd` (default `z`/`zi`, never `--cmd cd`). Keep README and THIRD-PARTY license tables in sync. `tests/shell-cli-tools.sh` uses isolated mocks without zsh, pacman or real tools.
- **New monitor notification:** `hl.on("monitor.added")` in `autostart-common.lua`
  calls `monitor-settings.sh notify`, which stays quiet for known monitors and in a
  young session, where `machine-layer-check.sh` reports it instead. One notification
  per monitor: a dock with two new screens fires two events and each run sees both,
  so runs take a `flock` and skip a monitor announced in the last 30 s
  (`$XDG_RUNTIME_DIR/archenemy-new-monitors.notified`); `tests/monitor-settings.sh`.
- **Wallpapers cover every monitor:** primary gets v1, all others get v2. A monitor
  with no saved wallpaper takes secondary's on `--restore`.
- **Main TUI keys (Super+A):** `[p]` opens autostart (programs), and `[u]` opens
  update archenemy. Keep labels, groups, state, previews and dispatch in sync.
- **Alacritty copy on select:** `[c] terminal` in Super+A edits only
  `[selection].save_to_clipboard` in the active `~/.config/alacritty/alacritty.toml`.
  `scripts/appbinds/terminal-settings.sh` keeps the first-change `.bak`; preserve
  every other config line and leave Alacritty's live reload alone. Refuse writes
  when the resolved file is inside the repository, including rice symlinks.
- **TUI look: `scripts/appbinds/lib/tui.sh` is the only palette.** One accent per
  rice (`tui_accent_code`) plus bright state colours; plain ANSI blue is 2.6:1 on
  `white-blue`. New screens start with `tui_header`, and `tui_fit` sizes columns,
  because bash `printf %-Ns` counts bytes. A new rice must pass
  `tests/tui-contrast.sh`.
- **A green `✓` in the TUI comes after the effect was read, never before.**
  `[a]`/`[e]`/`[d]` read `appbinds.lua` back and only then reload
  (`finish_bind_change` in `appbinds.sh`): `✓ Added / Changed / Removed` needs a
  reload without new errors, a config error restores the file, no answer from
  Hyprland gives `Saved: …`, and a failed write is reported without a reload.
  `workspace-mode-switch.sh` reads `data/workspace-mode.dat` back (a failed save
  puts the old `workspaces-monitors.lua` back and exits 1, because the guard,
  `ws-scroll.sh` and waybar read the mode from that file), prints the mode line
  after the reload result and `✓ Orphan guard started` only when `pgrep` sees
  the process after the start (`ARCHENEMY_GUARD_SETTLE`, default 1 s); exit 2 =
  saved but not confirmed. `[v]`/`[l]`/`[t]` end in `bar_change_report`: `✓` only when
  the rice has the module, waybar runs and `pkill -x` delivered the signal,
  otherwise `Saved: …` with when the bar will show it; a waybar older than its
  config gets `pkill -USR2 -x waybar` (reload) instead of the module signal. `write_dat`
  (`lib/tui.sh`) returns 0 only after reading the value back. The tests force
  failures without root tricks: `ulimit -f` with `SIGXFSZ` ignored, and `mv`,
  `pgrep`, `pkill`, `setsid` mocks in `tests/appbinds-menu.sh`.
- **After changing a Hyprland config from a script, use
  `scripts/hypr/lib/hypr-apply.sh`** (`hypr_reload_checked`): success means no
  new `hyprctl configerrors`, not the exit code of `hyprctl reload`. Read
  `hypr_config_errors` BEFORE writing the file and pass it as the first
  argument: Hyprland's autoreload picks the file up through inotify before
  `hyprctl reload`, so errors read after the write already contain the new
  error and the reload looks clean. Super+T (`lib/switch-rice.sh`) reloads the
  same way and only says "applied" after a clean reload.
- **App launcher: `scripts/rofi/rofi_drun.sh` is the only way to open
  `rofi -show drun`.** On Enter with no match rofi runs the typed text as a
  command and has no option to disable that in drun mode, so the script sets
  `-run-command` to a gate that only runs commands found in a `.desktop` `Exec=`.
  `tests/rofi-drun.sh`.
- **The waybar launcher has two modes: the distro glyph (default) and the Æ logo.**
  `custom/launcher` runs `scripts/waybar/launcher-logo.sh` (`"exec"`,
  `"return-type": "json"`, `"format": "{}"` — a fixed format would drop the
  script's text —, `"signal": 12`, no `interval`: with `signal` alone Waybar
  0.15.0 `custom.cpp` runs the script once and again only on
  `pkill -RTMIN+12 waybar`). The script reads `data/launcher-logo.dat`
  (`archenemy`; anything else, a missing file or garbage = `distro`) and prints
  `{"text":"<glyph>","class":"distro"}` or `{"text":" ","class":"archenemy"}`
  (one space: a custom module with empty text is hidden) and always exits 0.
  The glyph comes from os-release through `_pkg_os_file`/`_pkg_os_value` in

  the choice.** BlueZ ≥ 5.65 defaults to `[Policy] AutoEnable=true`
  (`plugins/policy.c`, `policy_adapter_probe`): every controller it finds — at
  boot, on hotplug or re-registration after resume, after a `bluetoothd`
  restart — is powered on; rfkill unblock powers on unconditionally
  (`src/rfkill.c` → `btd_adapter_restore_powered`); on SIGTERM `bluetoothd`
  powers adapters OFF itself (`adapter_shutdown`, emits `Powered` false before
  the name is lost); `/var/lib/bluetooth/<adapter>/settings` stores no power.
  Do not "fix" this in `/etc/bluetooth/main.conf` automatically (system file;
  README documents `AutoEnable=false` only as an explicit, reversible step) or
  with `rfkill block` (BlueZ then refuses `Powered=true`). Design in
  `scripts/waybar/bluetooth.sh`: `data/bluetooth-power.dat` (`on`/`off`, exact
  bytes via `od` — bash `read` drops NUL) is the source of truth. System
  events open a WINDOW (15 s): stream start (from `bluetoothd` start, `ps -o
  etimes=`; unknown age = from now), `InterfacesAdded`/`Removed` of
  `/org/bluez/hciN` (not `dev_*`), `NameOwnerChanged org.bluez`, logind
  `PrepareForSleep(false)`, a controller appearing or leaving `off-blocked` in
  the snapshot. In it the state is aligned to the file once and no→yes with
  `off` is undone (≤ `ENFORCE_MAX`=3 power calls per window, retry 1 s, never
  saved). Outside it every `Powered` change is saved after `CONFIRM` (2 s) if
  it held and no system event came in between; `PrepareForSleep(true)` and
  `PrepareForShutdown(true)` freeze saving. Windows hang on events every bar
  sees, so several streams decide alike — do not add per-stream windows (a new
  bar would undo what another bar saves). Right-click writes the file BEFORE
  `bluetoothctl power` (and restores the old file on failure), so the stream
  never undoes it; unwritable `data/` = exit 1, nothing changed. One `show`
  per batch (`tick` → `render "$snap"`); timers via `read -t` from
  `/proc/uptime` (monotonic, counts suspend). Tests: `bash tests/bluetooth.sh`
  (one FIFO per stream via `MOCK_EVENTS`, `ps` mock with
  `$MOCK_ROOT/bluetoothd_age`, `ARCHENEMY_BT_WINDOW`/`_CONFIRM` only with
  `ARCHENEMY_TEST=1`). In stream tests wait until the stream's only child is
  the listener before `killpg` — a render's `python` still exiting prints
  "Terminated" on stderr.
- **Bluetooth stream edge cases (B4; `expect` cases F1–F9 in
  `tests/bluetooth.sh` do not abort the suite).** A change seen outside a
  window is pending for `CONFIRM` s and announced in
  `$XDG_RUNTIME_DIR/archenemy-bluetooth.pending` (`on|off <uptime deadline>`;
  `data/` fallback, so a deadline further than `CONFIRM` ahead is stale): a
  stream's first snapshot adopts a fresh entry equal to the current state
  instead of enforcing the old file (a waybar restart right after a bluetui
  off). The entry is left behind on exit on purpose — the restarted bar must
  see it.

- **Window titles are untrusted data.** `hyprctl clients` prints them unfiltered, so a
  newline in a title forges list lines. Validate the address and PID before storing
  them or building a Lua expression, and never `eval` stored state

- **`asusctl` 6.3.8+ has subcommands only:** `asusctl profile next`, `asusctl profile get`.
  `asusd` starts from a udev rule and its unit has no `[Install]`: `systemctl start`, not
  `enable`. ASUS packages come from pacman (`install/asus-installation.sh`), never the AUR;

- **Monitor positions are logical pixels** (after scale and rotation), and Hyprland only
  warns about overlapping monitors ("this will cause issues"), so `scripts/hypr/monitor-settings.sh` asks mode,
  scale, then position and refuses overlaps. A scale saved as `1.33` (the `.dat`, older
  `hyprctl` output) is 160/120 inside Hyprland, so `logical_size` snaps it to the 1/120 grid: a 2560 panel at `1.33` is
  1920 wide, not 1925, and an exact fit must not be refused as an overlap. Functions in that
  script return explicit codes: a bare `return` after a failed test returned 1 and ended the
  dialog silently before the position question (2026-11-13). Renumbering (`r`) never moves a
  screen. Every position form has a test that compares the choice with the `.dat`, the

## Security rules — installer, AUR, updater

The installer runs code fetched from git with sudo and builds AUR packages,
so these rules are tested, not just conventions:

- **`install.sh` never runs as root** (EUID guard at the top): it asks for
  sudo itself, and makepkg/yay must never build AUR packages as root. It
  drops the cached sudo password on every exit: an `EXIT` trap with
  `sudo -k` right after platform detection — only where the run uses sudo
  (Arch, also with `--skip-packages`; Fedora without it). NixOS and Fedora
  with `--skip-packages` never call sudo, not even `sudo -k`
  (`USES_SUDO=0`); nothing before platform detection calls sudo. A later `trap … EXIT` (the step [3]
  `monitors.new` cleanup) replaces it, so every such trap must keep
  `sudo -k` (`bash tests/install-guards.sh`).
- **AUR goes through `install/lib/aur.sh` only.** yay is cloned from the
  fixed AUR URL (no environment override) and built in a fresh
  `mktemp -d` (never a fixed `/tmp/yay`) that is removed on every path,
  with an optional PKGBUILD review; `yay -S` offers an opt-in `--diffmenu
  --answerdiff All`. Reviews use a pager with a fallback (`$PAGER`, `less`,
  `more`, `cat`) — a fresh Arch has no `less`. Ctrl+C in the build subshell
  must stop the installer: clean up, then re-raise the signal (`trap - INT;
  kill -INT "$BASHPID"`), never `exit 130` (`bash tests/install-aur.sh`).
- **Test hooks never redirect real `sudo` writes.** The GPU and VirtualBox
  installers read `ARCHENEMY_ETC_DIR`, `ARCHENEMY_MODULES_DIR` and
  `ARCHENEMY_SYSMODULE_DIR` only with `ARCHENEMY_TEST=1`; a new hook of
  that kind gets the same gate and a check in `tests/install-guards.sh`.
- **Package lists:** `requirements-*.txt` never contain `-git` packages
  (they build an unreviewed HEAD); a pacman name must be in the official
  repos, an AUR name in the AUR and not in the official repos
  (`bash tests/packages-exist.sh`, one AUR RPC request; offline → `skip`).
  Step [5] counts a package as installed only under its own name
  (`pacman -Qq <name>` must print that name), never through a provider such
  as `swayosd-git` (`bash tests/install-requirements.sh`).
- **Updater (`scripts/appbinds/update-archenemy.sh`):** before the pull it
  lists the incoming commits and warns when `install/` or `packages/`
  change, and repeats a short summary right above "Run install.sh now?",
  which defaults to No. A stash conflict means no ✓ and no installer
  offer. Its git advice must work as printed: after a `stash pop` conflict
  `git add` + `git stash drop`, and never `drop` when nothing was applied
  (`bash tests/update-archenemy.sh` runs the advice on real git).
- **shellcheck with a baseline:** `bash tests/shellcheck.sh` runs
  `shellcheck -x -S info -e SC1091` on every tracked script and fails only on
  findings that are not in `tests/shellcheck.baseline`. Keep `-x`: without it
  shellcheck follows `source` only into files in the same call, so the result
  depended on which files `xargs -n 4` put together (a new file once turned a
  variable read by a sourced library into a false SC2034); check a single file
  the same way, from the repo root. Fix new findings in
  the code instead of adding them to the baseline: `--update-baseline` only
  removes fixed entries, and a deliberate exception goes in by hand with a
  `#` comment. A broken or killed shellcheck is a ✗, never a pass. Run it
  with `LC_ALL=C.UTF-8`; a comment line starting with the word `shellcheck`
  is a directive, so don't wrap prose onto such a line.
- **Secrets and machine data:** `bash tests/secrets.sh` (private keys and
  tokens in tracked files; the git history through `gitleaks` when it is
  installed) and `bash tests/repo-hygiene.sh` (interface names,
  `/home/<login>` paths) — the repository is public.

## How to write code here

- Don't guess Hyprland/waybar API, flags, or option names — open the source
  or the man page and check.
- Scope discipline: do exactly what was asked. See something else broken —
  report it, don't fix it without being asked.
- Small steps. A big architectural change → post a short plan first,
  implement after it's approved.
- Match the style of existing scripts: `=====` header-frames, ANSI color
  variables, `set -uo pipefail` in installers (no `-e` — optional steps
  must not abort the run).
- **Language:** `.md` documentation in this repo (README, AGENTS,
  CONTRIBUTING) — **English**. Code comments and commit messages —
  **Polish**. Identifiers (variables, functions, file names) — **English**.
  UI text in the appbinds TUI (Super+A) and the power menu (Super+Shift_R)
  — **English** (a deliberate exception, not an inconsistency).

## Testing — what "CI" means here

CI (`.github/workflows/tests.yml`) runs `bash tests/run-all.sh` in an
`archlinux` container on pushes to `dev`/`main` and on pull requests, with
read-only permissions and no third-party actions. It only complements the
levels below: installation, sudo, Hyprland and hardware are still checked
on a real machine. Verification has three levels:

1. **Syntax** — `bash -n <script>` for every touched script; for `.lua`
   files, check via `lua5.4`/`loadfile` (if available in your environment).
2. **Logic on a dummy** — symlinking/generation can be tested against a
   fake `~/.config` tree in a temp directory, without touching the real
   system. The machine layer has a ready-made suite: `bash
   tests/machine-layer.sh` runs the generators, the orphan guard, the mode
   switcher, the self-check and installer step [3] against a fake
   `hyprctl` (`tests/mock/hyprctl`, replaying a real dump), and `bash
   tests/wallpaper-switcher.sh` drives `Super+W` against a fake hyprpaper
   daemon built into the same mock. **Run both after any change to
   `install.sh` [3]–[8b], `scripts/hypr/`, or
   `rofi_wallpaper_switcher.sh`, and extend them when you add a consumer of
   `data/monitors/*.dat`** — the mock has three scenarios (renamed
   connectors, external monitor unplugged, two identical monitors) and a
   new consumer needs all three. **`bash tests/run-all.sh` runs every
   suite** (updater on real git, rice switcher, per-rice autostart on a
   fake `hl` API, GPU installer on a fake `/etc`, repo hygiene, …) — keep
   it green. Each suite gets `RUN_ALL_TIMEOUT` seconds (default
   `ceil(600 × ARCHENEMY_TEST_TIME_SCALE)`; an explicit value is final, `0` = no
   limit) and is then killed and reported as a suite timeout ("timeout
   pakietu", not "hung"), so a suite must not wait for input (its stdin is
   `/dev/null`). A failing suite's full log and `.rc` stay in
   `/tmp/archenemy-run-all-*` (paths printed with the last 200 lines) — read
   the full log before guessing. Harness watchdogs and readiness waits in a
   suite go through `tests/lib/timing.sh` (`test_timeout <base s> …`, then
   `test_timing_init "$T"` and `test_timing_ok` in the result line) or
   `tests/lib/test_timing.py` (`seconds()`, `wait_until`, `Lines`), scaled by
   `ARCHENEMY_TEST_TIME_SCALE` (1..10, default 1); wait for a state (file, log
   line, PID) with a deadline instead of a bare `sleep`. **Never scale a
   product timing contract** (doctor < 5 s, probes 4/4.5 s, Bluetooth render
   < 1 s, debounce/reconnect, the 15 s monitor trial): check it separately
   and label it `KONTRAKT`; an expired watchdog says `ZABEZPIECZENIE`
   (`tests/README-timing.md`). In suites with `pipefail`, capture a script's output into a
   variable instead of `… | grep -q` (SIGPIPE turns a pass into a fail).
   A suite that must prove it writes only under its `$T` calls
   `test_isolate "$REPO/tests/<suite>.sh" "$@"` right after sourcing
   `tests/lib/environment.sh` and checks `test_escapes "$T"` before its
   result line (overlay namespace, D7F R3; 2 = isolation unavailable → say
   so, never ✓). Write mocks with the Write tool, never nested heredocs in a
   shell command; `chmod` only regular files in a mock `bin` that also holds
   symlinks to real tools (`chmod` follows them into `/usr/bin`).
   The `*_REV` parity runs prove only what README "Verification" → "Known
   limits of the automated proof" lists; extend that list (or the parity) when
   a change touches a path no parity covers, never claim more.
3. **The real test** — `install.sh` and rice switching (`Super+T`) need a
   live Arch + Hyprland machine. If you don't have one, **say so
   explicitly** and write out exact "live-only" steps for a human to check
   instead of claiming something works.

## Definition of Done

A task isn't done until:

- touched scripts pass `bash -n` and add no new shellcheck findings
  (`bash tests/shellcheck.sh`; logic verified on a dummy where possible;
  `bash tests/machine-layer.sh` green when the machine layer was touched);
- things testable only on a live machine are named explicitly as
  "live-only", with concrete steps to check;
- `README.md` is updated (file tree and descriptions match reality);
- `packages/requirements-*.txt` / `additional-packages-*.txt` are updated
  if a config/script started (or stopped) needing a binary;
- zero machine data or secrets in tracked files or commit messages.

Report explicitly which points you checked off and which couldn't be
verified — and why.

## Branches and commits

- **`dev` → `main`.** New work lands on `dev`. `main` must always stay
  stable and bootable — only things verified on a live machine go there,
  and only with the consent of whoever maintains that repo/fork.
- One commit = one logical change. Format: `type: description in Polish,
  imperative mood`, e.g. `fix: popraw sprzątanie symlinków przy zmianie
  rice'a`, `docs: zaktualizuj drzewo plików w README`. Types as in
  Conventional Commits (`feat`, `fix`, `docs`, `refactor`, …), description
  in Polish.
- **Before `git checkout -- <file>` / `restore` / `reset`, check
  `git diff HEAD -- <file>`.** The working tree can be dirty despite a
  "clean" status at session start (someone else's uncommitted work from an
  earlier session). Don't pull someone else's changes into your commit —
  split them out separately.
- Each operator settles `git commit` rights in the local repo with their
  own agent. Regardless of that arrangement: **never `push --force`, never
  merge `dev` → `main` without explicit human approval**, never commit
  machine data/secrets (see DoD).
- Don't append a tool footer (`Co-Authored-By`, `Generated by …`) to the
  commit message unless the repo operator explicitly asks for it — author
  identity is their call, not the agent's.

## Pull requests

CI runs only the shell suites (see "Testing"). If you're working through a
pull request (rather than directly on `dev`), state explicitly in it: what
was verified automatically (`bash -n`, dummy tests) and what remains
"live-only" for the reviewer to check on a real Arch + Hyprland machine —
the reviewer has no other way to find out.

## When you don't know

Say "I don't know" and ask, or check the source. Don't fill the gap with
plausible-sounding code or a flag name.

Every new TUI choice screen must support ↑/↓, j/k, Enter and Esc through the shared `tui_menu` function in `scripts/appbinds/lib/tui.sh`, preserving existing letter and number shortcuts.

The keyboard layout order (`Super+A → [k] → 2`) is one `tui_menu` screen per place (`pick_layout_order` in `appbinds.sh`); the whole order typed as numbers on the first screen (`2 1`, Enter) stays as a shortcut. With `TUI_MENU_CAPTURE_DIGITS=1` on a terminal `tui_menu` reads the typed line through readline, pre-filled with the first digit, so the whole line is visible; a pipe gets the plain `read`. A helper script written by a test must not be named after a Python standard module (`pty.py` shadows `pty`).

Shared menus collect multi-digit choices through Enter when there are more than nine items and scroll to fit the terminal. Confirmations reject digits. Autostart labels use global app numbers and no numbers on action rows. Removing a bind requires confirmation with default No.

Managed shell plugin/CLI files use a checksum independent of the current template; unsigned v1 CLI files are recognized with the frozen `config/shell/cli-tools-v1.tsv` catalog. Keep that catalog and `shell_plugins_v1_text` unchanged for migration. Plugin package prompts default to No, CLI package prompts to Yes; both require a separate confirmation.

A new Super+A main-menu entry needs a row in `tests/tui-effects.list` naming the check that reads the resulting state (a `.dat`, a generated file, the mock's answer). `bash tests/tui-effects.sh` fails without it, and also when a monitor position form loses its read-back test or `monitor-settings.sh` gains a bare `return`. A test that only sees the menu open or a command being called does not count as a test of the effect.
