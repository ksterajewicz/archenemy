# AGENTS.md

Instructions for AI agents (Claude Code, Copilot, Cursor, and others — whatever
tool each contributor uses) working on this repository. Goal: every agent,
regardless of operator and tool, should keep the project consistent and break
nothing. This file is the single source of such instructions in the repo —
there's no `CLAUDE.md` or other per-tool file here; if your agent reads a
different format, start from this file and point it here.

## Before you start — session start

1. Read `README.md` (repo structure, the four layers, installation).
2. Check `packages/requirements-*.txt` and `packages/additional-packages-*.txt`
   — what's actually supposed to be installed.
3. If the task touches an unfamiliar module — open it and read it before
   writing a line of code.
4. Don't assume something works the way its name suggests — verify against
   the source (the repo's code, or Hyprland/waybar documentation), not from
   memory.

## Stack

- Bash (scripts) + Hyprland configuration in **Lua** (as of Hyprland 0.55 the
  old hyprlang `.conf` format is deprecated; old files stay alongside as
  `*.conf.bak` until the migration is fully verified on a live machine —
  `hyprlock.conf` and `hyprpaper.conf` deliberately STAY in hyprlang, they're
  separate programs, not Hyprland).
- One component in C: `src/flux-wall/` — the animated wallpaper (Wayland
  `wlr-layer-shell` + EGL + GLES 3.0). Optional: built by `install.sh` step
  [9.6] with a fallback; a missing compiler/dependency doesn't block the
  rest of the install.
- No repo-level build system (aside from `make -C src/flux-wall`) and no
  custom package manager — everything goes through `pacman`/AUR (`yay`),
  with lists in `packages/`.

## Architecture — four layers (NEVER mix them)

| Layer | Where it lives | In git? |
|---|---|---|
| **Rice** (looks) | `rices/<name>/`, symlinked into `~/.config` | yes |
| **Shared** (binds, media keys, general Wayland env) | `config/hypr/*.lua` | yes |
| **Machine** (monitors, GPU env, hardware keys, workspaces) | generated by `install.sh` into `config/hypr/` | NO (gitignore) |
| **Personal** (user autostart, user app binds) | `config/hypr/autostartpersonalisation.lua`, `config/hypr/appbinds.lua` | NO (gitignore) |

The optional music stack (`config/mpd/`) follows the same split: `mpd.conf` is
shared (tracked), `output.conf` (audio output, rewritten by `Super+A → [o]`) is
machine, `local.conf` is personal — both generated by `install.sh` [8l] and
gitignored. `config/applications/ncmpcpp.desktop` is a tracked template that
[8l] *copies* (never links) into `~/.local/share/applications`.

Rules that follow directly from the table:

- No monitor names, GPU vendors, hostnames, or personal apps in tracked
  files. If something like that shows up in your diff — that's a sign it
  should be generated, not committed.
- `install.sh` must create EVERY generated file (even empty ones) — the
  rices' `hyprland.lua` `require()`s/`source`s them, so a missing one breaks
  startup.
- New machine/personal content → add the pattern to `.gitignore`.

## Known pitfalls (don't rediscover them twice)

- **waybar `custom/*` module `interval` MUST be an integer (seconds)
  ONLY.** Waybar 0.15.0 casts the fraction to `long` BEFORE multiplying by
  1000 — `0.5` becomes **1 ms**, i.e. a fork loop of the script running
  non-stop, separately on each monitor. Always force an immediate module
  refresh via a signal (`pkill -RTMIN+N waybar`) from the state-changing
  action, never by shortening the interval.
- **Rice switching is 2-line stubs** in
  `scripts/changing-theme-scripts/*.sh` (the file name = the rofi menu
  label; the `RICE_NAME` inside must match the `rices/<folder>` folder
  name). ALL the logic lives in `scripts/changing-theme-scripts/lib/switch-rice.sh`
  — edit the library, never paste logic back into a stub (that's how
  copy-paste parity drift happens).
- **Machine generators are a single source of truth**:
  `scripts/hypr/lib/gen-workspaces.sh` and `gen-autostart.sh` are called
  from both `install.sh` and the live switchers (`workspace-mode-switch.sh`).
  The same goes for `install/bootloader.sh` (sourced by the CPU/kernel
  installers). Don't duplicate this logic across scripts.
- **Switching rice removes ALL symlinks in `~/.config` pointing into
  `rices/` before linking the new rice.** Without this, the previous rice's
  theme leaks through folders the new rice doesn't overwrite. Preserve this
  invariant whenever you change the switcher.
- **`white-blue` / `tron` parity:** every NON-visual change (functionality,
  binds, sources, window rules, script hooks) goes to BOTH at once, never
  to just one. `white-blue_beta` is legacy — bug fixes ONLY for what it
  already has; don't extend it with binds/modules/sources it never had.
  Purely visual/GUI changes stay per-rice by design.
- **Workspaces have two modes** (`shared`/`decades`, state in
  `data/workspace-mode.dat`). Changing one of the four {generator
  `gen-workspaces.sh`, binds in the generated `workspaces-monitors.conf`,
  orphan guard `scripts/hypr/workspace-orphan-guard.sh`, waybar's
  `hyprland/workspaces` module} requires checking the other three.
- **The hyprlock background and the wallpaper (`hyprpaper.conf`) are the
  machine layer**, even though they look like rice config — both are
  generated files, sourced (`source = `) from each rice's
  `hypr/hyprlock.conf` / `hyprpaper.conf`. Never write wallpaper/background
  state directly into `rices/` folders.
- **The music stack (mpd/mpc/ncmpcpp/mpv) is a recommendation, never a
  requirement** (owner's rule, 2026-09-20): packages stay in
  `additional-packages-*.txt`; `install.sh` [8l] runs only when the binaries
  exist, asks before enabling any service (default N), never replaces an
  existing user config without an explicit `y` (and then keeps a `.bak`),
  and is a no-op on a second run. Keep every new piece of it opt-in.
- **ncmpcpp writes into `ncmpcpp_directory`** (`error.log`, `patterns.list`).
  Its default is `~/.config/ncmpcpp/` — a symlink into `rices/` — so every
  `rices/*/ncmpcpp/config` MUST set `ncmpcpp_directory` outside the repo
  (`~/.local/share/ncmpcpp/`), or the working tree gets dirty. Colors in
  those configs are 1-based (`9`–`16` = bright ANSI); `bindings` lives in
  `white-blue` and the other rices symlink to it (like `networkmanager-dmenu`).
- **mpd's output switch must rewrite `config/mpd/output.conf` and restart
  mpd** — `mpc enable/disable` does not survive a restart, because mpd's
  state file only *disables* outputs on read (`src/output/State.cxx`: the
  `1` state is a no-op; enabled-ness comes from the config). `Super+A → [o]`
  never stops PipeWire/WirePlumber and rolls back to pipewire when ALSA
  fails; keep it that way — an exclusive `hw:` device takes the whole
  desktop's audio with it.
- Any binary used in a config or script must be covered by
  `packages/requirements-*.txt` (required) or
  `packages/additional-packages-*.txt` (optional — guarded with
  `command -v X && X`). Don't add dependencies "while you're at it" — every
  new one needs a stated reason.

More architectural context (the full file tree, workspaces, keyboard
shortcuts) is in `README.md` — that's the source of truth for the repo's
structure, this file only adds behavioral rules.

## How to write code here

- Don't guess Hyprland/waybar API, flags, or option names — open the source
  or the man page and check.
- Scope discipline: do exactly what was asked. See something else broken —
  report it, don't fix it without being asked.
- Small steps. A big architectural change → post a short plan first,
  implement after it's approved.
- Match the style of existing scripts: `=====` header-frames, ANSI color
  variables, `set -uo pipefail` in installers (no `-e` — optional steps
  must not abort the run).
- **Language:** `.md` documentation in this repo (README, AGENTS,
  CONTRIBUTING) — **English**. Code comments and commit messages —
  **Polish**. Identifiers (variables, functions, file names) — **English**.
  UI text in the appbinds TUI (Super+A) and the power menu (Super+Shift_R)
  — **English** (a deliberate exception, not an inconsistency).

## Testing — what "CI" means here

There's no pipeline. Verification has three levels:

1. **Syntax** — `bash -n <script>` for every touched script; for `.lua`
   files, check via `lua5.4`/`loadfile` (if available in your environment).
2. **Logic on a dummy** — symlinking/generation can be tested against a
   fake `~/.config` tree in a temp directory, without touching the real
   system.
3. **The real test** — `install.sh` and rice switching (`Super+T`) need a
   live Arch + Hyprland machine. If you don't have one, **say so
   explicitly** and write out exact "live-only" steps for a human to check
   instead of claiming something works.

## Definition of Done

A task isn't done until:

- touched scripts pass `bash -n` (logic verified on a dummy where
  possible);
- things testable only on a live machine are named explicitly as
  "live-only", with concrete steps to check;
- `README.md` is updated (file tree and descriptions match reality);
- `packages/requirements-*.txt` / `additional-packages-*.txt` are updated
  if a config/script started (or stopped) needing a binary;
- zero machine data or secrets in tracked files or commit messages.

Report explicitly which points you checked off and which couldn't be
verified — and why.

## Branches and commits

- **`dev` → `main`.** New work lands on `dev`. `main` must always stay
  stable and bootable — only things verified on a live machine go there,
  and only with the consent of whoever maintains that repo/fork.
- One commit = one logical change. Format: `type: description in Polish,
  imperative mood`, e.g. `fix: popraw sprzątanie symlinków przy zmianie
  rice'a`, `docs: zaktualizuj drzewo plików w README`. Types as in
  Conventional Commits (`feat`, `fix`, `docs`, `refactor`, …), description
  in Polish.
- **Before `git checkout -- <file>` / `restore` / `reset`, check
  `git diff HEAD -- <file>`.** The working tree can be dirty despite a
  "clean" status at session start (someone else's uncommitted work from an
  earlier session). Don't pull someone else's changes into your commit —
  split them out separately.
- Each operator settles `git commit` rights in the local repo with their
  own agent. Regardless of that arrangement: **never `push --force`, never
  merge `dev` → `main` without explicit human approval**, never commit
  machine data/secrets (see DoD).
- Don't append a tool footer (`Co-Authored-By`, `Generated by …`) to the
  commit message unless the repo operator explicitly asks for it — author
  identity is their call, not the agent's.

## Pull requests

The repo has no CI. If you're working through a pull request (rather than
directly on `dev`), state explicitly in it: what was verified
automatically (`bash -n`, dummy tests) and what remains "live-only" for
the reviewer to check on a real Arch + Hyprland machine — the reviewer has
no other way to find out.

## When you don't know

Say "I don't know" and ask, or check the source. Don't fill the gap with
plausible-sounding code or a flag name.
